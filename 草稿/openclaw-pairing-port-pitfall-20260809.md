# 手机连不上自家服务器：一次 OpenClaw 节点配对的端口代理陷阱

## 素材（来自今天上午真实排障）

现象：手机 App 手动配对 OpenClaw 网关，主机/端口/令牌都填了，证书指纹也对上并点了「信任」，最后界面还是报「连接问题 / 无法访问您的 Gateway」。

排障三步：
1. 网关健康检查：openclaw status 全部正常，ws 可达、auth token 正常
2. 证书指纹：从 thinkspc.fun:8443 抓的 Let's Encrypt 证书算 SHA-256，与手机要求一致
3. 关键发现：网关日志里 11:43~11:49 之间没有任何来自手机的 WS 连接记录 → 连接请求根本没到网关

根因：device-pair 插件 publicUrl 配置的是 wss://thinkspc.fun/gateway（默认 443 端口），但服务器 nginx 的 443 端口 / 路径代理到的是 Halo 博客（127.0.0.1:8090），只有 8443 端口才代理到 OpenClaw 网关（127.0.0.1:18789）并带 WebSocket upgrade 头。

为什么证书信任能通过：443 和 8443 用的是同一张 LE 证书，TLS 握手成功 → 信任对话框正常出现 → 但 WS 升级请求被 443 转发给了 Halo → 连接问题。

修复：publicUrl 改成 wss://thinkspc.fun:8443，重新配对，openclaw nodes approve 放行，成功。

附加坑：
- bootstrap token 10 分钟过期，过期要重新生成
- 手动设置里端口默认填 18789 是内网端口，公网连接必须走 8443
- 443 是「看起来对」的默认端口，恰恰是最容易踩的坑

三条经验：
1. 证书信任通过 ≠ WebSocket 能通，TLS 和 WS 是两回事
2. 服务器日志里没有连接记录 = 请求根本没到服务，先查代理层而不是应用层
3. 多端口公网服务器，先确认每个端口的反代目标，别信默认端口
