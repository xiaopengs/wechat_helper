# SCQA 与故事线设计

## SCQA 四要素写法

| 要素 | 写法要点 | 常见错误 |
|---|---|---|
| S 情景 | 无争议的事实，1-2 句，建立共识 | 写成背景综述，越长越糟 |
| C 冲突 | "但是"后面那句：变化/痛点/反常识 | 冲突不痛，读者无感 |
| Q 疑问 | 读者视角自然产生的问题 | 问成"我想做的"而非"读者关心的" |
| A 答案 | 一句话核心主张，可被下层支撑 | 主张含糊（"应该重视"）或塞多个论点 |

SCQA 必须压缩在 100 字内讲完——序言是钩子，不是摘要。

## 四种序言变体

| 变体 | 结构 | 适用场景 |
|---|---|---|
| 标准式 | S→C→A | 常规分析报告 |
| 开门见山式 | A→S→C | 读者时间极碎（领导只想听结论） |
| 突出忧虑式 | C→S→A | 危机沟通，冲突比背景更抓人 |
| 突出信心式 | Q→S→C→A | 说服持怀疑态度的读者 |

向上汇报默认开门见山式：第一句就是答案，SCQA 往后放。

## 故事线：一条主线钉进脑子

大读者记不住技术细节，只记得一句话。设计主线三步：

1. **开场钩子（数据冲击）**：把最大的差距/浪费/收益压成一句话数字。例："我们用 800MB 存储干 100MB 的活。"
2. **中间全部服务主线**：每一页都要能回答"这和主线有什么关系"；答不上来的内容进附录。
3. **收尾愿景（格局抬升）**：从"解决一个 bug"抬到"建设一种能力"。例："公共库只是统一技术底座的第一步。"

钩子开场 + 愿景收尾，中间的方案细节才有附着点。

## 执行摘要写法（金字塔顶）

一页，三个模块，总字数 ≤300：

1. **核心主张**（一句话，带量化结论）；
2. **三个发现**（支撑主张的三个最有力的点，各配一个数字）；
3. **一个请求**（明确到可批准的程度：谁、多久、做什么、如何止损）。

自检：把执行摘要单独抽出来发给没看过全文的人，他能说出"这是什么、为什么重要、要我做什么"——三个都过关才能用。

## 主线一致性检查

- [ ] 开场钩子的数字与正文测算一致？
- [ ] 每一页标题都能挂到主线上？
- [ ] 收尾愿景没有引入正文没铺垫过的新承诺？
